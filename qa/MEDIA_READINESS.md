# Odruky P3 — source inventory and protected-pixel verification

Two independent **read-only** gates are used. Neither tool publishes, edits source photographs, approves media, or marks the site RELEASE_READY.

## Gate A: original-source authenticity and completeness

```powershell
node qa/media-readiness.cjs --manifest "<original-assets-manifest.json>" --media-dir "odruky/media"
node qa/media-readiness.cjs --manifest "<original-assets-manifest.json>" --media-dir "odruky/media" --enforce
node --test qa/media-readiness.test.cjs
```

- Uses the exact required assets and their SHA-256 hashes from the supplied source manifest.
- Missing, invalid-JPEG, changed-byte or not-publication-approved sources mean `BLOCKED`. `--enforce` exits 2 when blocked; otherwise the audit emits JSON.
- A historical V6 SHA mismatch is **not evidence of worse quality**; it can also mean a later customer original. Its provenance requires explicit reconciliation; the tool cannot automatically authorize it.
- Real source photographs retain their original dimensions. **A portrait original is valid as a source** when its SHA matches. A 3:2 aspect ratio is not an authenticity requirement. The output records `SOURCE_PREFLIGHT_ELIGIBLE` (not release ready) only when the entire declared required source inventory and publication policy pass.
- The JSON field `galleryNeedsWideDerivativeIds` identifies present gallery originals that are not 3:2 and need a separately checked 3:2 derivative. `posterIds` lists poster sources (F12) separately: poster source dimensions do not inherit the 3:2 gallery rule.
- Empty or inconsistent required inventories, duplicate or unsafe IDs, unknown required-media purposes, and invalid SHA metadata fail closed.
- `releaseReady` is **always false**, even on eligible source-only inventories.

## Gate B: decoded pixel equality inside 3:2 wide derivatives

```powershell
$env:PLAYWRIGHT_MODULE = 'C:\Projekty\Odruky-browser-qa\node_modules\playwright'
$env:PLAYWRIGHT_BROWSERS_PATH = 'C:\Projekty\Odruky-browser-qa\browsers'
node qa/preserved-pixels.cjs --pairs "<pixel-pairs.json>" --original-dir "<customer-originals>" --wide-dir "<wide-derivatives>"
node --test qa/preserved-pixels.test.cjs
```

Pair manifest is explicit about the original, the original SHA-256, the PNG wide derivative and its nonnegative pixel placement. No image is selected by filename guessing:

```json
{
  "pairs": [
    {
      "id": "F02",
      "originalFile": "customer-F02.jpeg",
      "originalSha256": "<64 SHA-256 hex characters of approved original>",
      "wideFile": "F02-wide.png",
      "x": 150,
      "y": 100
    }
  ]
}
```

- The original may be JPEG/PNG. The derived **wide file must be PNG** with a real PNG signature. A JPEG derivative would lose exact RGB pixel equality during recompression.
- Chromium decodes both images independently. The verifier requires exactly 3:2 dimensions on the wide PNG and pixel-perfect RGBA equality at the declared `x,y` rectangle for **every pixel** from the original source.
- Only pixels outside the original rectangle may change. Different placement, changed source hash, changed protected pixel, invalid geometry, false PNG extension, missing file or unsafe path produces `BLOCKED` and CLI exit 2.
- `PIXEL_SUBSET_VERIFIED` means only **the declared pairs** match. It never proves complete gallery coverage, legal approval, customer sign-off or production readiness. No wide derivatives are generated by this QA code.

## Real snapshot: historical V6 manifest versus current customer Drive

The historical V6 manifest still reports 27 required sources (26 gallery + 1 poster F12): 8 byte-exact against historical V6, 15 SHA-256 mismatches and 4 missing: **F10, F12, F24, F26**. That comparison is intentionally preserved as historical provenance evidence; a mismatch means only “different from the supplied historical manifest”, not “the web modified the file”.

On 2 November 2026 the 15 mismatching IDs **F01, F02, F03, F04, F06, F09, F13, F14, F16, F17, F20, F21, F22, F23, F25** were independently downloaded as raw bytes from the currently connected customer Google Drive. For every one of the 15 files, SHA-256, byte length and computed Git blob SHA-1 matched the corresponding `odruky/media/Fxx.jpg` blob on repository main `c62afa2b5c543606b75ae4acef21d7bb779cd66f`. Therefore these 15 repository files are **byte-identical copies of the current customer Drive sources**; they are not recompressed or transformed web copies. The durable evidence is `qa/current-customer-media-provenance.json` and its regression test.

This does **not** authorize publication. The four missing sources remain missing and the historical publication policy is still `publicationApproved: false`. Of the existing gallery originals, **17 are non-3:2** and require separate origin-pixel-preserving wide-derivative verification:

`F02, F03, F08, F09, F14, F16, F17, F20, F21, F22, F23, F27, F28, F29, F31, F33, F34`

The real state therefore remains **BLOCKED**. CSS cropping, recoloring or `object-fit: cover` is not a legitimate replacement for verified wide derivatives.

## Integration and release limitations

These tools run in an isolated local worktree. The tests use temporary synthetic fixtures; no customer images have been silently transformed or approved. Both outputs are for **audit**, not live website changes.

Before publication: retain the verified current-Drive provenance for the 15 byte-identical repository sources; deliver or explicitly resolve F10/F12/F24/F26; verify true wide-derivative pixel preservation and completeness; confirm publication rights, customer acceptance, correct contact/operator/legal/GDPR data, exact-SHA central BWNG on a **committed** revision and separate authorized release.

Local Node/browser PASS does not substitute for central BWNG. No DNS/Webnode/production changes or automatic Git merge/push are implied.
